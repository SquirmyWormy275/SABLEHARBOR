# Persistent company-source journey candidate

`PersistentCompany` creates one independent company lifetime from an exactly accepted source baseline before any engagement exists. It copies source bytes once using ordinary reads/writes, preserving all original business dates, real import dates, provenance, commands, input digests, versions and system-owner registrations. It never copies an audit state or manufactures company facts during `Engine.create`. A source root can outlive and serve successive or concurrent engagements.

`PersistentAudit(world, routes)` accepts multiple business families within one explicit branch. One fresh engagement can therefore perform successive security, identity, continuity or privacy methods over the same shared company source; routes do not force separate workrooms per family. Additional engagements have their own fresh engines, IDs, memberships, evidence, workpapers, populations, samples and findings. Earlier company grants/access/collection journals do not populate a later audit. Normal company activation, kickoff, grants, PBC issuance, Engine-bound discovery, supported clock advancement and typed exact-version `company.collect` remain the interface. A retained audit original never follows a later company correction.

This candidate has not activated an evolving Sable Harbor successor. The original independently accepted 1783-version V2.1 database remains sealed. Its migration/model limitations remain in native bodies. V3, new company systems, new record families, full-company authorization and wider corporate/year source sufficiency remain pending. Initial admission is an exact reviewed baseline; evolution currently permits only dated append-only corrections to existing native records in already registered systems. New systems, owner replacement and historical record mutation fail closed.

The old frozen-library adapter acceptance explicitly does not authorize this runtime. Production requires a separately pinned review with schema `SH_ROOT_PERSISTENT_COMPANY_RUNTIME_REVIEW_V1`, verdict `PASS_SHARED_APPEND_ONLY_COMPANY_RUNTIME_SELECTED_BOUNDARY`, `source_execution_authorized=true`, exact `runtime_module_sha256`, exact reused `adapter_module_sha256`, and `accepted_baseline_pins` equal to the complete dictionary returned by the passed `AcceptedLibrary.verify()`. Each initial successor correction additionally requires a separately pinned source review with schema `SH_ROOT_COMPANY_SOURCE_OPERATION_REVIEW_V1`, verdict `PASS_COMPANY_OWNED_APPEND_OPERATION_SELECTED_BOUNDARY`, the same exact baseline pins, `company_operator_id`, and the SHA-256 of canonical `CompanyStore._json(operation)` bytes. This conservative first admission contract is not a general company-operation scheduling system.

The operation includes exact company, branch, system, record, expected predecessor version, command ID, event time, availability time, content SHA, provenance and synthetic origin. The company operator supplies independently useful ordinary business bytes; audit IDs, grading cues and prepared answers do not belong in that body. The trusted company writer is distinct from the engagement's access operator, auditor and reserved reviewer. `CompanyOperator` is an in-process capability, not a public authentication endpoint. No external API or deployment is introduced.

A successful append records actual authorization, import and completion times; source dates cannot move backward. The new version and command/input digest bind an ordinary immutable receipt and a new immutable checkpoint. The checkpoint includes the predecessor checkpoint SHA and all append receipt pins. Existing baseline rows and all four immutable triggers must remain exact. Reopening the company requires an explicitly supplied latest checkpoint path and hash retained by the trusted operator outside editable company state; the runtime never accepts a locally resealed checkpoint automatically. A stale checkpoint rejects a newer source until the authorized operator supplies its exact successor pin. After a crash between database append and receipt sealing, an unreceipted version fails closed; this candidate does not silently roll back, checkpoint, delete or repair it.

Independent review rejected the preserved first code candidate `8d5fabc8`: fully resealed replay could accept a backdated successor, boolean predecessor version or extra operation field that normal append rejected. The corrected candidate shares `validate_operation` between admission and replay. Both require exact operation keys, a strict integer current predecessor, valid native identities/origin/provenance and typed bounded bytes, publication at or after the business event, and successor event/publication clocks at or after their exact predecessor. Replayed native clocks must equal normalized operation clocks and the actual import clock must remain canonical. Regression probes repair all native, input, receipt and checkpoint digests and provide the repaired external checkpoint pin; invalid operations must still fail. The original candidate, neutral proof and reviewer probes remain unchanged.

All normal CompanyStore connections acquire a reentrant thread mutex and a private advisory process lock. This serializes legitimate DELETE-journal transactions across concurrent engagements. Before and after normal source API connections, the runtime verifies accepted custody and rejects any `-wal`, `-shm` or `-journal`, including dangling symlinks. A malicious writer that ignores the advisory lock is detected through sidecars or changed native/schema custody. No diagnostic operation deletes or checkpoints its sidecars. These mechanics are a trusted local boundary, not a sandbox against a hostile process controlling the entire workstation.

Neutral engineering mode is deliberately restricted to exclusively `NEUTRAL-*` company identities and JSON bodies marked `engineering_neutral_fixture=true`. It cannot admit the Sable Harbor library or a later real company body. Hypothetical review-contract fixtures in tests are explicitly labeled as engineering fixtures, never actual independent acceptance. The disposable neutral proof creates a company, collects version 1 in audit one, appends a January 10 event available January 11 independently, creates audit two with zero evidence despite prior company journals, rejects future discovery at January 3, then records audit two's ordinary January 12 clock advance and collects version 2. Audit one's retained bytes stay unchanged. Both engagements coexist; their source grants are eventually revoked.

Meaningful tests cover that actual journey, concurrent reads, stale/reopened custody, distinct actors, branch/reviewer isolation, unavailable corrections, substituted owner registrations, bad predecessor/typed bytes, resealed receipt/checkpoint attacks, held-open WAL shadows, and exact runtime/source-operation review bindings. Separate read-only verification opens no normal mutable CompanyStore connection. This proves local persistence/custody mechanics only: no task completion, independent professional conclusion, corporate recovery, historical marker restore, real PHI or live operation is asserted. The independent reviewer must approve this candidate before any Sable Harbor successor activation.
