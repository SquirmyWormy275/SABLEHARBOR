# SABLE HARBOR — CCF CONTROL RECORD SCHEMA

**Schema ID:** `SH-CCF-CONTROL`  
**Version:** 0.1.0

This is the canonical logical schema for common controls and their local implementations. It is intentionally richer than a conventional spreadsheet control matrix so the same data can later drive Markdown, Excel, SQL, APIs, benchmark packages, and audit evidence without losing provenance.

## 1. Common control record

| Field | Required | Meaning |
|---|---:|---|
| `control_id` | yes | Stable ID, format `SH-<DOMAIN>-NNN` |
| `version` | yes | Semantic version of control definition |
| `title` | yes | Short business-language name |
| `primary_domain` | yes | One domain from CCF taxonomy |
| `secondary_domains` | no | Additional related domains |
| `control_objective_id` | yes | Stable objective served by the control |
| `business_objective_ids` | yes | Enterprise/business objectives protected |
| `risk_ids` | yes | Risks mitigated or monitored |
| `control_statement` | yes | What Sable Harbor does/ensures |
| `business_rationale` | yes | Why the control exists absent any audit |
| `applicability_rule` | yes | Machine-readable/structured scope condition |
| `control_owner_role` | yes | Accountable role, not necessarily a named person |
| `performer_role` | yes | Role(s) that operate it |
| `challenge_role` | no | Independent review/challenge role where applicable |
| `frequency_or_trigger` | yes | Continuous, event-driven, per transaction, daily, monthly, etc. |
| `control_nature` | yes | Manual, automated, IT-dependent manual, hybrid |
| `control_function` | yes | Preventive, detective, corrective, directive, recovery |
| `key_control` | yes | Enterprise key-control designation with rationale |
| `financial_reporting_relevance` | yes | none, indirect, direct, potentially material |
| `customer_service_relevance` | yes | none, supporting, direct |
| `security_privacy_relevance` | yes | none, supporting, direct |
| `operational_safety_relevance` | yes | none, supporting, direct |
| `evidence_expectation` | yes | Natural records expected from operation |
| `system_dependencies` | no | Systems/services required for operation |
| `upstream_dependencies` | no | Other controls/processes relied upon |
| `downstream_dependencies` | no | Controls/processes that rely on this one |
| `failure_modes` | yes | Credible ways the control can fail |
| `exception_process` | yes | How deviations/waivers are authorized and tracked |
| `effective_date` | yes | Date this version becomes operative |
| `superseded_date` | no | End of validity |
| `status` | yes | draft, approved, effective, suspended, retired |
| `canon_basis` | yes | Canon sections/decision IDs/business facts supporting existence |
| `framework_mappings` | no | Directional mappings, never equivalence claims |
| `notes` | no | Controlled explanatory notes |

## 6. Risk record

Use cause-event-impact structure and preserve inherent/residual state. Required minimum fields are `risk_id`, `title`, `category`, `cause`, `event`, `impact`, `affected_objectives`, `applicability`, `owner_role`, `challenge_role`, `inherent_likelihood`, `inherent_impact`, `velocity`, `existing_control_ids`, `residual_likelihood`, `residual_impact`, `tolerance`, `kris`, `effective_date`, and `status`.

## 7. Identifier rules

- IDs are immutable after publication.
- Titles and text can change only through versioning.
- Retired controls remain addressable.
- Local implementations never reuse the parent control ID as their sole identity.
- Framework IDs never become Sable Harbor control IDs.
- A control split creates new IDs and retires the old definition; it does not silently rewrite history.

## 8. Minimum quality gates before a control becomes EFFECTIVE

A control cannot become effective unless:

1. business rationale exists;
2. at least one risk/objective relationship exists;
3. applicability is explicit;
4. owner and performer roles are identified;
5. frequency/trigger and expected evidence are defined;
6. credible failure modes are documented;
7. exception handling is defined;
8. canon basis does not conflict with locked decisions;
9. external mappings, if any, identify exact versions and non-equivalence;
10. the effective date and control version are set.

This schema deliberately does not require a SOC mapping, sample size, audit procedure, or test result for a control to exist.
